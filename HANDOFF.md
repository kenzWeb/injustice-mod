# HANDOFF — контекст проекта для агента на новой машине

Читай этот файл первым. Он заменяет переписку, в которой всё это делалось.
Задача на сборку — в [PROMPT.md](PROMPT.md).
Разбор соло-рейдов и античита — в [docs/solo-raid.md](docs/solo-raid.md).

## Что это

Твик-меню для **Injustice 2 Mobile 6.7.1 (iOS)** на джейлбрейкнутом устройстве (сборка под **rootless**: Dopamine / palera1n)
владельца. Цель — видеть HP в бою автоматически, без ручного поиска значений
сканером памяти, плюс пара переключателей.

Всё, что здесь есть, получено **статическим анализом** расшифрованного бинаря.
Никаких догадок в офсетах нет: каждый выведен из дизассемблера, ниже указано
откуда.

## Целевой бинарь

| | |
|---|---|
| Путь в IPA | `Payload/Injustice2Mobile.app/Injustice2Mobile` |
| Формат | Mach-O 64, `MH_EXECUTE`, **ARM64** (arm64e-слайса нет) |
| Размер | 98 МБ, `__text` 66 МБ |
| Шифрование | снято, `LC_ENCRYPTION_INFO_64.cryptid = 0` |
| UUID | `2c66bd15-78e2-3cab-b3f6-2be3ff279a18` |
| Bundle ID | `com.wb.Injustice.Brawler2017` |
| CFBundleVersion | `1438123`, short `6.7.1` |
| Image base | `0x100000000` |
| Движок | **Unreal Engine 4 (~4.27)**, не Unity — IL2CPP-метаданных нет |

Важная особенность: сегмент `__TEXT` начинается с `vmaddr 0x100000000, fileoff 0`,
поэтому **RVA численно равен файловому смещению**. Удобно для патчеров.

Символы C++ и RTTI вырезаны полностью — из 3879 записей symtab только 613
определённых, все из сторонних ObjC-SDK.

## Откуда взялись имена и офсеты

Аналогом `Il2CppDumper` для UE служат статические таблицы рефлексии
`UECodeGen_Private` в `__DATA_CONST,__const` плюс восстановление аргументов
на вызовах `GetPrivateStaticClassBody` (`0x102531110`, 4661 вызов). Оттуда
получены 3714 `UClass` с размерами и суперклассами, 2760 `UScriptStruct`,
1425 `UEnum`, 11183 `UFunction` (9670 с адресами нативных exec-функций) и
29016 смещений полей.

Инструменты и выгрузка **остались на исходной Windows-машине** в
`dump/tools` и `dump/out` — в этот репозиторий они не клались, для сборки
твика не нужны. Если понадобятся, их надо запросить у владельца.

## Ключевая находка

**HP не является `UPROPERTY`** — в таблицах рефлексии его нет, только геттеры.
Офсеты сняты из самих геттеров.

`ACombatCharacter` (размер `0x1DC0`), наследование
`ACombatCharacter : ABaseGameCharacter : ACharacter : APawn : AActor : UObject`:

| Офсет | Тип | Что | Источник |
|---|---|---|---|
| `+0x4E4` | int32 | CurrentHealth | `GetHealthPercentage` RVA `0x1B4CFB4` |
| `+0x4E8` | int32 | MaxHealth | там же |
| `+0x1240` | int32 | BaseHealth | `execGetBaseHealth` RVA `0x210D978` |
| `+0x1244` | int32 | BaseModifiedHealth | RVA `0x210D924` |
| `+0x1248` | int32 | AdditiveModificationsHealth | RVA `0x210D8D0` |

`GetHealthPercentage` грузит оба поля как `ldr s0` + `scvtf` — то есть в памяти
это **знаковые int32**, а не float. Для сканера памяти тип поиска — Dword.

### Функции боя

Все адреса — RVA настоящих нативных функций, а не exec-переходников. Переходник
ловит только вызовы из Blueprint, поэтому для каждой функции адрес доставался
дизассемблированием exec и взятием последнего «не-хелперного» `bl`.

| RVA | Функция | Как получен |
|---|---|---|
| `0x1B50954` | `ACombatCharacter::SetCurrentHealth(int32)` | поиск `str w,[x,#0x4E4]` в функции с двумя `csel` |
| `0x1B4CFB4` | `ACombatCharacter::GetHealthPercentage()` | exec `0x210AFF4` → `bl` |
| `0x1B4D8D8` | `ACombatCharacter::ShowDamageMessage(float, ...)` | exec `0x2110D00` → `bl` |
| `0x1B4062C` | `ACombatCharacter::TakeCombatDamage(float, float, ...)` | exec `0x210B560` → `bl` |
| `0x1B57088` | `ACombatCharacter::DamageCharacter(ACombatCharacter*, float, ...)` | exec `0x210B70C` → `bl` |

### Энергия и стоимость приёмов

Power и Energy **не поля персонажа** — они живут в компонентах
`UCombatCharacterPower` / `UCombatCharacterEnergy` (оба наследуют
`UCombatCharacterResource`, размер `0x128`).

Layout компонента подтверждён напрямую, `x0` в exec — это сам ресурс:

| Офсет | Что | Источник |
|---|---|---|
| `+0xF8` | текущее значение (float) | лист-функция `0x3745874`: `ldr s0,[x0,#0xF8]; ret` |
| `+0xFC` | максимум (float) | `execGetMaxResource 0x211ED20`: `ldr s0,[x0,#0xFC]` |

**Важное предупреждение о ложном следе.** В `ResourceComponent::GetCurrent`
(`0x1B7C83C`) видно `ldr x8,[x0,#0xB00]` / `#0xB08`, а в энергетическом
аналоге `0x1B7CBD8` — `#0xBB0` / `#0xBB8`. Соблазн принять их за смещения
компонентов внутри `ACombatCharacter` — ошибка: до этой функции `x0` дважды
преобразуется вызовами, и это уже не персонаж. Проверка по дампу подтверждает:
по `+0xB00` у `ACombatCharacter` лежит `ShieldBreakerParticleData`, а не
указатель. Поэтому твик **не ходит по этим указателям**, а хукает методы
персонажа, где `x0` гарантированно `ACombatCharacter`.

Гейты приёмов (все `bool f(ACombatCharacter*, ECombatAttackType)`):

| RVA | Функция |
|---|---|
| `0x1B4E914` | `HasEnoughFundsForSpecialAbility` |
| `0x1B4E874` | `HasEnoughPowerForSpecialAbility` |
| `0x1B4E8C4` | `HasEnoughEnergyForSpecialAbility` |
| `0x1B457A0` | `HasEnoughResourceForSpecialAbility` |
| `0x1B4DEA8` | `float GetPowerPercentage(ECombatAttackType)` |
| `0x1B4E0F0` | `float GetCurrentPower()` |
| `0x1B4E110` | `float GetCurrentEnergy()` |

Приёмы в этой игре ограничены **стоимостью ресурса, а не таймером**, поэтому
снятие гейта убирает и «ожидание между приёмами» — отдельного кулдауна нет.

### Требования испытаний

Требование описано структурой `FBattleRequirementData` (0x88) — восемь массивов:
`CharacterTypeRequirements` (+0x00), `BaseCharacterRequirements` (+0x18),
`CardTierRequirements` (+0x28), `CardClassRequirements` (+0x38),
`CharacterTagRequirements` (+0x48), `CharacterTeamRequirements` (+0x58),
`CharacterAlignmentRequirements` (+0x68), `CharacterGenderRequirements` (+0x78).

Вычисляет их **RVA `0x1C99C38`**, найденная через
`UEditTeamMenu::UpdateBattleRequirementsStates` (exec `0x214D5DC` → реальная
`0x1E950D0`, вызов на `0x1E95188`).

ABI нестандартный: функция возвращает `TArray<bool>` **косвенно через `x8`**
(у `TArray` нетривиальный деструктор, поэтому возврат идёт через скрытый
указатель независимо от размера). Подтверждается прологом: `mov x20, x8`,
затем `stp xzr, xzr, [x20]`. Обычным C-прототипом это не выражается, поэтому
хук — `__attribute__((naked))`-обёртка: сохраняет `x8`, вызывает оригинал,
затем проходит по возвращённому массиву и выставляет все байты в 1.

`UBattleRequirement` — **не** логика, а UMG-виджет строки требования
(`UComponentBase : UScreenReaderUserWidget`, размер совпадает с родителем,
своих полей нет). На него не смотреть.

Вычислитель вызывается из **пяти** мест (`0x1E53464`, `0x1E95188`, `0x1F47AD0`
и дважды из самой функции старта боя `0x1F49A94` — на `0x1F4AD70` и `0x1F4B110`),
поэтому один хук покрывает и отображение, и проверку внутри старта.

**Но галочек мало.** Эмпирически: после хука обе панели показывают требования
выполненными, а в бой всё равно не пускает. Причина — отдельный флаг
`UPreFightMenu +0x750` (не отражён, обычный C++ bool перед `mCurrentGeometry`).
В `0x1F625DC` он выставляется как `eor w8, w20, #1` → `strb w8, [x21, #0x750]`,
то есть хранит **инверсию** «требования выполнены».

`UPreFightMenu::OnFightButtonClicked` (exec `0x2282A40` → реальная `0x1F4D690`,
`x0` = меню, `w1` = IgnoreCheckArtifactCharges) читает его:

```
ldrb w8, [x19, #0x750]
cmp  w8, #1
b.ne 0x1F4D6EC        ; != 1 -> tail call 0x1F49A94, настоящий старт боя
```

Поэтому второй хук обнуляет `+0x750` перед вызовом оригинала.

**Но и этого мало.** Настоящий гейт находится внутри самого старта боя
`0x1F49A94`:

```
0x1F4AC70  bl   0x1F640EC       ; x0 = данные требований, x1 = команда
0x1F4AC74  tbz  w0, #0, 0x1F4AD00   ; не выполнено -> собрать и показать попап
```

`0x1F640EC` — переходник на 12 байт (`mov x2, x19; mov x3, #0; b 0x1C998FC`).
Настоящий предикат — **`0x1C998FC`** (528 байт, соседствует с вычислителем
`0x1C99C38`), сигнатура
`bool f(FBattleRequirementData*, team, context, flags)`.

Оба вызова вычислителя внутри `0x1F49A94` (`0x1F4AD70`, `0x1F4B110`) **решения
не принимают** — они лишь заполняют `URequirementsPopupData`: тексты в `+0x48`,
состояния в `+0x58`. Именно поэтому попап показывал проставленные галочки и
одновременно отказывал: галочки идут из вычислителя, а решение — из
`0x1C998FC`.

Порядок отладки, который сработал: найти ветку в попап (`tbz` на `0x1F4AC74`),
а не гадать по флагам. Три предыдущие попытки были потрачены на следствия.

### Итог проверки: упирается в сервер

Клиентский замок снят полностью и проверен на устройстве: попап не появляется,
кнопка срабатывает, старт боя запускается. Дальше игрока **выбрасывает в главное
меню** — это обработка отказа сервера.

```
StartChallengeBattleResponse   size 0x168
   +0x0000  bool                          bAllowedToStart
   +0x0008  TArray<FCharacterDefinition>  PlayerCharacters
   +0x0018  TArray<FCharacterDefinition>  AICharacters
   +0x0028  FBattleData                   Battle
```

Сервер получает запрос на старт, сверяет состав с требованием и отвечает
`bAllowedToStart = false`. Никакие клиентские правки на это не влияют.

Подделка этого поля бессмысленна даже технически: в том же ответе приходит вся
раскладка боя — `PlayerCharacters`, `AICharacters`, `FBattleData`. При отказе они
пустые, поэтому «разрешить» старт локально означает войти в бой без данных боя.

**Дальше по этому направлению не копать.** Граница проходит здесь и она
серверная.

### Серверная античит-телеметрия

`FBattleValidationData` (0x4C) приходит в ответах на завершение боя
(`CompleteArenaBattleResponse +0xDC`, `CompleteRaidBattleResponse +0x1B0`):

```
+0x04 int32 PlayerCheatCount        +0x1C float PlayerEffectiveDamageReceivedRatio
+0x08 float CheatDetectionScalar    +0x20 float BattleDuration
+0x0C bool  IsValid                 +0x24 float PlayerBasicsPerSecond
+0x0D bool  UsedAutoPlay            +0x28 float PlayerSwapsPerSecond
+0x10 float OpponentThreatRatio     +0x2C float PlayerSpecialsPerSecond
+0x14 float PlayerDPSRatio
```

Игра штатно измеряет ровно те величины, которые меняет этот твик. Это надо
учитывать при оценке любых новых функций, а не считать, что клиентские правки
никем не наблюдаются.

### Авто-прохождение кампании

Две стадии, обе клиентские, бой при этом **реально происходит** и штатно уходит
на сервер — убирается только ожидание.

1. **Завершение боя.** Здесь была допущена ошибка, стоившая версии 1.6.0, —
   стоит запомнить. Хук `SetCurrentHealth` **пассивен**: он меняет запись HP,
   но не вызывает её. Пока игрок не бьёт противника, игра ему HP не пишет,
   поэтому ни авто-победа, ни авто-завершение не срабатывали вовсе. По той же
   причине не работал и отсчёт начала боя: он вёлся из `IMNoteCombatTick()`,
   вызываемой только при публикации HP.

   Активная точка — `ACombatCharacter::GetHealthPercentage` (`0x1B4CFB4`):
   она дёргается каждый кадр для полоски здоровья, на игровом потоке, с живым
   `this`. Из неё и публикуется HP (поэтому HUD теперь обновляется постоянно,
   а не только при уроне), и вызывается `SetCurrentHealth(character, 0)` для
   не-игроков, когда условие завершения выполнено. Кэшировать указатели не
   потребовалось.

   **Вторая ошибка, тоже стоит запомнить:** сначала из этого тика вызывался
   `SetCurrentHealth(character, 0)`. HP визуально обнулялось у всех врагов, но
   бой вставал намертво — никто не мог бить и матч не заканчивался. Причина:
   запись числа обходит боевой конвейер, а гибель персонажа запускается именно
   им. Персонаж оказывался «мёртв по числу, жив по логике».

   Правильная процедура — **`0x1B41710`**, найденная через реальный
   `CheatKillAI` (`0x1B4179C`), который к ней и сводится. Она не пишет HP, а
   строит событие урона и прогоняет его штатно:

   ```
   ldr   x8, [x20]         ; vtable жертвы
   ldr   x8, [x8, #0xa78]  ; виртуальный метод -> максимум HP
   scvtf s0, w0            ; величина урона
   bl    0x1B6D0A4         ; нанести урон
   ```

   Сигнатура `f(causer, victim, instigator)`; в `CheatKillAI` первый и третий
   аргумент совпадают. Жертва — текущий не-игрок, источник — последний
   виденный персонаж игрока: он обновляется в том же тике каждый кадр, поэтому
   указатель всегда свежий.

   `_Thread_local` флаг `sInAutoFinish` обязателен: обработка смерти дёргает
   полоску здоровья и без него ушла бы в рекурсию.

   Условие завершения — `IMAutoCampaignShouldFinish()`: с начала боя прошло
   больше заданной задержки. Начало боя фиксируется в `IMNoteCombatTick()`,
   если предыдущая публикация HP была больше `kStaleMs` назад.
   Задержка настраивается (по умолчанию 1.5 с), а не нулевая — мгновенное
   завершение даёт `BattleDuration` около нуля, что видно в
   `FBattleValidationData`.

2. **Экран наград.** `UMatchResultsPopup::OnTransitionInAnimFinished`
   (exec `0x220FFD4` → реальная **`0x1F3957C`**) даёт живой `this` сразу после
   анимации появления. Через 0.7 с из него вызывается
   `UMatchResultsPopup::OnContinue` (exec `0x2210120` → реальная
   **`0x1F39914`**).

Указатель на попап берётся из хука и используется в пределах секунды, пока
попап заведомо жив — то же правило, что и с персонажами: не хранить чужие
указатели дольше необходимого.

3. **Переход к следующему бою.** `UCampaignMenu::SetAndInitChapter`
   (exec `0x20B5780` → реальная **`0x1D46D88`**) срабатывает каждый раз, когда
   карта кампании инициализируется, и **приносит оба нужных значения сразу**:
   `x0` = меню, `w1` = индекс главы, `x2`+`w3` = `FName` текущего боя. Из них
   через 1.6 с вызывается `UCampaignMenu::OnSummaryWindowStartButtonClicked`
   (exec `0x20B5524` → реальная **`0x1D479B0`**).

`FName` здесь — 12 байт, передаётся по значению в двух регистрах. Подтверждено
по `execGetCurrentBattleId` (`0x20B575C`): `bl 0x1D476E8; str x0,[x19];
str w1,[x19,#8]` — то есть возврат идёт в `x0` (8 байт) + `w1` (4 байта).
В коде это выражено как `typedef struct { uint32_t part[3]; } IMFName`, и
clang раскладывает его по регистрам так же.

Указатель на меню используется через 1.6 с после инициализации, пока карта
заведомо жива. `IMAutoCampaignMayStartBattle()` не даёт срабатывать чаще раза
в 4 секунды — без этого повторная инициализация карты уводила бы в рекурсию.

4. **Кнопка «В бой» в предбоевом меню.** Между картой и боем есть ещё один
   экран, и одного шага 3 не хватает. `UPreFightMenu::UpdateOpponentView`
   (exec `0x22826C0` → реальная **`0x1F48668`**) даёт живой указатель на это
   меню, из него через 1.2 с вызывается `UPreFightMenu::StartFight`
   (exec `0x22823D4` → реальная **`0x1F49A94`**).

   `StartFight` — это **та же самая** функция, в которую делает tail-call
   `OnFightButtonClicked`, то есть настоящий старт боя, а не имитация нажатия.
   Она же содержит гейт требований, поэтому байпас требований на неё
   распространяется.

Каждый шаг имеет собственный ограничитель частоты
(`IMAutoCampaignMayStartBattle`, `IMAutoCampaignMayPressFight`, оба по 4 с) —
общий счётчик не годится, потому что шаги идут подряд и съедали бы бюджет
друг у друга.

Цикл останавливается сам: когда кончается энергия, игра показывает
`ShowEnergyReplenishPopup`, карта не переинициализируется, и хук не срабатывает.

### Авто-фарм соло-рейдов

**Главная находка: `UPreFightMenu` общий для всех режимов.** В нём есть
`SetRaidBossData(CurrentHealthPercent, CurrentHealth, MaxHealth, EBossPhaseType,
BossNameText)`, `SetPipRefreshTimer` и `SetState(EPrefightMenuCachedStateType)`,
а состояние рейда лежит в `UPreFightMenuCachedState_SoloRaid`. Поэтому шаги
2–4 авто-кампании (`UpdateOpponentView` → `StartFight` → экран наград →
`OnContinue`) работают в рейдах **без единой новой строки** — достаточно снять
гейт `IMAutoCampaign()` и пускать те же ветки при `IMAutoRaid()`.

Новой работы потребовали только вход в бой и почта.

**Точка входа — `USoloRaidManagementMenu`, RVA `0x1FFEC44`.** Виртуальный
метод, заполняющий окно сводки по боссу; статических вызовов у него нет (0
`bl`), но `MSHookFunction` по адресу перехватывает и виртуальную диспетчеризацию.
Сигнатура `f(USoloRaidManagementMenu*, URaidBossData*)` восстановлена целиком из
дизассемблера, и **каждое** поле совпало с таблицами рефлексии:

```
str x19, [x21, #0x338]   ; WindowData->RaidEnemyData
str s0,  [x21, #0x340]   ; CurrentHealthPercent
ldur d0, [x19, #0xb4]    ; BossHealthCurrent+BossHealthMax одной загрузкой
str x9,  [x21, #0x360]   ; BattleName
ldr x8,  [x20, #0x558]   ; this->mRootPanel
ldr x0,  [x8,  #0x370]   ; rootPanel -> URaidBossSummaryWindow
bl  0x1E4C578            ; URaidBossSummaryWindow::SetData
```

Отсюда и взят путь до окна сводки: `menu +0x558` → `+0x370`. Так же подтверждены
`URaidBossData`: `BattleIndex +0x30`, `BossHealthCurrent +0xB4`, `BossHealthMax +0xB8`.

**Запуск боя — `URaidBossSummaryWindow::OnStartButtonClicked`, RVA `0x1E4C0DC`**
(exec `0x229065C`). 24 байта, читается целиком:

```
ldr x8, [x0, #0x338]   ; mData
cbz x8, ret
ldr x1, [x8, #0x338]   ; mData->RaidEnemyData
add x0, x0, #0x380     ; делегат
b   0x1E4C5E0          ; broadcast
```

Он не имитирует нажатие, а вызывает тот же делегат, на который подписан
`URaidManagementMenu::OnStartBattleButtonClicked` (RVA `0x1F68838`). Поэтому бой
стартует штатным путём игры и уходит на сервер как обычно.

**Стоп по попыткам.** `menu +0x568` (`mRaidInfoPanel`) → `+0x370`
(`mAttemptsPipsBox`) → `CommonPipsCount +0x34C`, `BonusPipsCount +0x350`,
`PremiumPipsCount +0x354`. Сумма нулевая — цикл не запускается. Значения заодно
публикуются в оверлей.

**Второй стоп — `URaidManagementMenu::CanFight`, виртуальный слот `0x658`.**
Из exec `0x2296614`: `ldr x8,[x20]; ldr x8,[x8,#0x658]; blr x8; strb w0,[x19]`.
Вызывается через vptr самого объекта — тот же приём, что с `IsPlayerCharacter`.
Это **чтение решения игры**, а не его подмена: если игра сама считает бой
недоступным, фарм не лезет дальше.

Прочие виртуальные слоты `URaidManagementMenu` (сняты из 20-байтовых exec-
переходников вида `bl 0x2297DC0; ldr x1,[x8,#slot]; br x1`, где `0x2297DC0` —
общий пролог, а не реализация):

| Слот | Метод |
|---|---|
| `0x658` | `CanFight(URaidBossData*)` |
| `0x660` | `StartBattle()` |
| `0x668` | `StartSequence()` |
| `0x6B0` | `UpdateSubBosses()` |
| `0x6B8` | `UpdateMainBoss()` |
| `0x708` | `FinishSequence()` |

**Выбор босса — `URaidManagementMenu::SelectBoss`, RVA `0x1F69B64`** (exec
`0x22967C4`). Подтверждён дизассемблером против рефлексии:
`ldr x8,[x0,#0x4a0]` (`mBossActors`) → `ldr x8,[x8,w1,sxtw #3]` →
`str x8,[x0,#0x4b8]` (`SelectedBoss`). В текущей сборке не вызывается —
оставлен как готовый рычаг, см. «не проверено» ниже.

**Почта.** Награды приходят с сервера в `FRewardsReceipt` и падают в Inbox —
локально их не создать. Забирается всё кнопкой «claim all»:
`UInboxMenu +0x3C0` (`mClaimAllButton`), клик через уже имеющийся
`RVA_SimulateClick`. Живой указатель на меню даёт
`UInboxMenu::CreateInboxMessageData` — **RVA `0x1E9B244`** (exec `0x21B46D0`),
вызывается на каждое сообщение при открытии почты. Навигация в почту **не**
автоматизирована намеренно: она рвала бы боевой цикл, а награды в Inbox лежат
и ждут.

**Пауза боя вынесена отдельно от кампании.** `FCheatDetectionGlobalData` — это
`TMap<EGameModeType, FCheatDetectionData>`, то есть пороги в рейдах свои. Плюс
сервер хранит `lastBattlesDealtDamage` (ряд последних боёв) и
`LastWonBattleValidationDataPerLevel`, так что оценивается не отдельный бой, а
история. Поэтому `IMAutoRaidDelay` — своя настройка со своим значением по
умолчанию **12 с** против 3 с у кампании: бой с боссом, законченный за три
секунды, выпадает из собственной истории игрока куда заметнее, чем рядовой бой
кампании. Настройка вынесена в меню — снижать её осознанно.

Отдельные ограничители частоты, как и в кампании (общий счётчик не годится —
шаги идут подряд): `IMAutoRaidMayStartBoss` 6 с, `IMAutoRaidMayClaim` 10 с.

### Попытки: почему «безлимит» упирается в сервер

Запрос был — фармить без ограничения по попыткам и по уровню. Клиентского
рычага под это нет, и вот почему конкретно.

**Все четыре пула попыток серверные.** `CommonPipsCount`, `BonusPipsCount`,
`PremiumPipsCount` в `UAttemptsPipsBox` — поля **виджета отрисовки пипсов**
(`UAttemptsPipsBox : UComponentBase`, `mPipsBox +0x338` — это `UHorizontalBox`,
в который складываются иконки). Записать туда 99 значит нарисовать 99 кружков.
Сама величина живёт в серверном прогрессе и приходит с ответом.

Тренировочные бои — не обход: `FSoloRaidGlobalData.MaxAvailableTrainingAttempts`
(`+0x18`) и `FSoloRaidSeasonProgressionData.availableTrainings` (`+0x44`)
означают, что у тренировок свой лимит, тоже в серверной структуре прогресса.
`USoloRaidTrainingManager` (`UPlayerProfile +0xF0`) в рефлексии пустой — своих
полей нет.

Уровень — та же история: `ESoloRaidLevelState` (`Locked/Active/Passed`) это
отображение, а решение в `FSoloRaidProgressionData.currentLevel`, серверном.

**Решающая деталь — та же, что убила обход требований к испытаниям.**
`FStartSoloRaidBattleResponse` при отказе возвращает `bAllowedToStart = false`
**и пустые** `PlayerCharacters`, `AICharacters`, `FBattleData`. Подделать флаг
локально нечем помочь: входить будет не во что.

**Что всё-таки сделано.** `IMRaidIgnoreGates` («Игнорировать попытки рейда»)
снимает **все клиентские** проверки в цикле фарма: и стоп по сумме пипсов, и
`CanFight`. Это возможно потому, что `OnStartButtonClicked` (`0x1E4C0DC`) сам
никаких проверок не содержит — читается целиком, там только null-check `mData`
и broadcast делегата. То есть вызов идёт мимо состояния кнопки.

Дальше клиент штатно отправляет `StartSoloRaidBattle`, и решает сервер. Это и
есть окончательная проверка, где проходит граница:

- бой запускается и идёт → клиентские замки были единственными, безлимит работает;
- **выкидывает в главное меню** → сервер ответил `bAllowedToStart = false`,
  ровно как с испытаниями, и дальше копать в эту сторону нечего.

Второй исход ожидаемее. Симптом описан в разделе «Итог проверки: упирается в
сервер» — он один и тот же.

**Не проверено на устройстве.** Возврат к следующему боссу после боя: неизвестно,
перезаполняет ли игра окно сводки сама, или нужен тап по боссу. Статически это
не выясняется. Диагностика — счётчики в строке трассировки: `rs` (сводка
показана), `rg` (бой запущен), `cl` (почта забрана). Если после боя `rs` не
растёт, недостающее звено — вызов `SelectBoss` (`0x1F69B64`) из хука на слоте
`0x6B0` (`UpdateSubBosses`); адреса для этого уже собраны выше.

### Встроенные читы разработчиков

В релизной сборке остался `UCombatCheatManager` (94 функции): `CheatWin`
`0x211F2AC`, `CheatKillAI`, `CheatToggleUnlimitedPlayerSpecials`,
`CheatSetHealth` и прочие. Все exec-переходники сначала зовут `0x2121D80`,
затем tail-call в реальную реализацию (`CheatWin` → `0x1B417D8`).

**Не используются намеренно.** Для их вызова нужен живой экземпляр
`UCheatManager`, который UE создаёт не во всех конфигурациях, а это не
проверено. Авто-победа сделана через уже работающий хук `SetCurrentHealth`,
то есть противник умирает штатным путём игры, без зависимости от наличия
чит-менеджера.

Состав по категориям: матч/бой 7, HP и урон 23, энергия и суперы 17,
поведение ИИ 24, неуязвимость 4, отладка и HUD 17. Полезны как карта того,
какие рычаги в бою вообще существуют — многие функции указывают на
соответствующие обычные методы `ACombatCharacter`, которые и хукаются.

### Заморозка ИИ

`ACombatCharacter::IsStunned(EStunType)` — реальный адрес `0x1B490F8`
(exec `0x210C830`), `bool`, `x0` = персонаж. Хук возвращает `true` для
не-игроков: оглушённый персонаж не действует, но остаётся уязвимым.

`IsFrozen()` (`0x1B47CD0`) намеренно не трогается — заморозка в этой игре
влияет и на возможность попадания по цели, а не только на её действия.

ABI `ShowDamageMessage` проверен по прологу: `x0` = жертва, **`s0` = величина
урона** (`fmov s8, s0`, затем `fcvtzs w24, s8` для показа), `x1` = `&DamageEvent`,
`x2` = `DamageCauser`, `w3` = IsCrit, `w4` = IsLethalHit, `w5` = bTrueDamage.

Почему хукаются две функции, а не одна: `SetCurrentHealth` меняет HP, но
всплывающая цифра урона считается отдельно и раньше — если править только HP,
на экране показывается неизменённое число. Обе точки берут решение из одного
модуля `IMDamage`, поэтому разойтись не могут.

### Точка перехвата

**RVA `0x1B50954` = `ACombatCharacter::SetCurrentHealth(int32)`**, `x0` = объект,
`w1` = новое HP:

```
ldr  w8, [x0, #0x4e8]     ; MaxHealth
cmp  w1, w8
csel w8, w1, w8, lt       ; min(new, max)
cmp  w1, #0
csel w8, wzr, w8, lt      ; clamp к 0
str  w8, [x0, #0x4e4]     ; <- единственная запись CurrentHealth
bl   ...                  ; нотификации, проверка смерти, UI
```

Через неё проходят **все** изменения HP: урон, хил, инициализация боя. Прямых
`str w,[x,#0x4E4]` в бинаре всего 13, и 12 из них принадлежат другим классам с
совпавшим офсетом — эта единственная релевантная. Поэтому один хук видит всё.

### Как отличается свой персонаж от чужого

`ABaseGameCharacter::IsPlayerCharacter()` — **виртуальный**, слот vtable по
байтовому смещению `0x9A0` (из `execIsPlayerCharacter`: `ldr x8,[x0]` →
`ldr x8,[x8,#0x9a0]` → `blr x8`). Вызывается через vptr самого объекта.

Тупик, который уже проверен и отброшен: `CharacterTeam` (`+0x118C`) — это
**фракция ростера** (`JusticeLeague`, `SuicideSquad`, `MortalKombat`, …), а не
сторона боя. Для «свой/чужой» не годится.

## Архитектура

Код разбит по слоям, комментариев в исходниках нет намеренно — вся справочная
информация собрана здесь.

```
Tweak.xm            только %ctor: инициализация, проверка версии, установка хуков
src/Offsets.h       все RVA и смещения полей
src/IMRuntime       база образа, RVA→указатель, IsPlayerCharacter, чтение HP
src/IMSettings      всё состояние мода за атомарным API, без UIKit
src/IMDamage        чистая логика: решение по HP и по показываемой цифре
src/IMHooks         тела хуков и их установка
src/IMTheme         цвета, шрифты, метрики
src/IMRowBuilder    конструктор строк меню (тумблер, значение, кнопка, подпись)
src/IMOverlayWindow окно с passthrough hitTest
src/IMMenu          сборка и поведение меню
```

Зависимости идут строго в одну сторону: UI знает про `IMSettings`, хуки знают
про `IMSettings`, `IMDamage` и `IMRuntime`, но `IMDamage` не знает ни про UIKit,
ни про хуки. Благодаря этому решение об уроне принимается ровно в одном месте.

### Обязательное: `extern "C"` в заголовках для `Tweak.xm`

Theos компилирует `.xm` как **Objective-C++**, а весь `src/` — обычный
Objective-C. Голое объявление C-функции в заголовке, включённом из `Tweak.xm`,
попадает в C++-namespace и манглится (`IMHooksInstall()`), тогда как
определение в `.m` даёт C-символ (`_IMHooksInstall`). Линковка падает с
`Undefined symbols ... NOTE: found '_IMHooksInstall' ... declaration possibly
missing 'extern "C"'`.

Поэтому `IMHooks.h`, `IMRuntime.h`, `IMSettings.h`, `IMMenu.h` оборачивают
объявления функций в:

```c
#ifdef __cplusplus
extern "C" {
#endif
...
#ifdef __cplusplus
}
#endif
```

**Любой новый заголовок, включаемый из `Tweak.xm`, обязан делать то же самое.**
`@interface` ObjC-классов оставляют снаружи блока — им это не нужно.
`Offsets.h` не требует обёртки (одни макросы). Остальные заголовки
(`IMDamage.h`, `IMPresets.h`, `IMTheme.h`, `IMRowBuilder.h`,
`IMOverlayWindow.h`) включаются только из `.m`, смешения линковок нет.

До версии 1.1.0 проблемы не было, потому что весь код лежал в одном `Tweak.xm`.

### ARC и out-параметры

Не возвращать паттерн «out-параметр — указатель на ObjC-объект» без явного
`__strong`. Под ARC указательный out-параметр по умолчанию `__autoreleasing`,
и передача `&_ivar` (адрес `__strong` ivar) запрещена: `passing address of
non-local object to __autoreleasing parameter for write-back`. Если такой
параметр нужен, тип обязан быть `UITextField * __strong *`.

## Решения в коде и почему

1. **Один хук вместо патча инструкций.** Патчер офсетов (у владельца есть такой
   в тулзе) умеет только писать байты в код — показать значения он не может в
   принципе. Хук даёт и чтение, и подмену.
2. **Никаких обращений к файловой системе.** У владельца **rootless**-джейлбрейк; любой хардкод системных путей ломается. Настройки живут в
   памяти (атомики), prefs-plist и ресурсов бандла нет. Благодаря этому код
   одинаков для roothide/rootless/rootful — различается только упаковка.
3. **UI не разыменовывает указатели на персонажей.** Значения копируются в
   атомики внутри хука; иначе оверлей падал бы на устаревшем объекте после
   конца боя. Через 3 с без вызовов показывает `--`.
4. **Version lock.** `%ctor` читает `CFBundleVersion` и при несовпадении с
   `1438123` не ставит хуки вообще — чтобы не писать по чужим адресам после
   обновления игры.
5. **`Freeze HP (все)`** намеренно грубый: останавливает запись у всех, бой не
   закончится. Оставлен для наблюдения, не для игры.
6. **Все модификаторы применяются только при `delta > 0`**, то есть когда HP
   реально уменьшается. Это не косметика: `SetCurrentHealth` вызывается и при
   инициализации боя, и раньше `One-hit kill` обнулял противника ещё до начала
   матча — тот стоял с 0 HP, не бил и не получал урона.

## Если игра обновится

Все RVA слетят. Порядок пересчёта описан в [README.md](README.md); коротко:

1. заново снять дамп (`dump/tools/emit.py` на исходной машине);
2. найти `SetCurrentHealth` — искать в `__text` инструкцию
   `str w, [x, #<CurrentHealth>]` внутри функции, которая ещё и грузит
   `+<MaxHealth>` и клампит двумя `csel` (скрипт `find_hp_sites2.py`);
3. слот `IsPlayerCharacter` — дизассемблировать `execIsPlayerCharacter` и
   прочитать смещение в `ldr x8, [x8, #...]`;
4. обновить `kExpectedBundleVersion`.
